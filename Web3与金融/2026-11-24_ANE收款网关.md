# ANE收款网关

## 一句话摘要
> 用一台安卓手机监听支付宝/微信的收款通知，把「到账」翻译成易支付回调发给你自己的业务系统——用你本人的收款码，不经手资金，也不调官方支付 API。

## 核心分析与要点

- **核心内容**：ANE（Automated Notification-Driven Epay）是一个自托管的收款订单匹配服务。链条是三段：Android 客户端读系统通知 → 服务端按**渠道 + 实付金额 + 订单有效期**匹配订单 → 按经典易支付协议向业务系统发回调。它兼容易支付的 MD5 签名协议，对外提供 `/submit.php`（网页下单跳收银台）、`/mapi.php`（建单返回 JSON）、`/api.php?act=order`（查单）三个入口，现有接易支付的系统基本可以无痛换过来。

- **关键亮点 / 结论**：
  - **绕开了"官方支付 API 需要商户资质"这道门槛**：它不接支付宝/微信的开放接口，而是靠安卓手机读通知栏来判定到账，因此个人收款码也能自动化——这是它存在的全部理由，也是它全部风险的来源。
  - **多商户/多应用模型设计得清楚**：每个应用独立密钥，同一商户的应用共享设备与对应渠道的优惠池，支付宝与微信额度互相独立；服务端通过签名识别是哪个应用。
  - **运营侧功能不少**：Web 面板可筛订单、看实收汇总与回调日志、导出 CSV、按邮箱配通知偏好，还能看设备心跳与上报状态、订阅收款/回调失败/设备离线/持续离线提醒。
  - **接入文档写了两条容易踩的规矩**：签名要排除 `sign`、`sign_type` 与空字段，按参数名 ASCII 升序拼 `key=value&` 再追加密钥算 MD5；回调走 GET，业务方必须验签、校验金额、幂等处理并回 `success`——**浏览器返回页不能代替服务端回调**。
  - **工程规范度超出它的年龄**：仓库 2026-11-16 才创建，但已有 Go 1.24 + Node 22 + Android SDK 36 的完整构建链，CI 输出带 SHA-256 的服务端包与 APK，GPL-3.0，并附第三方素材声明。

- **适用场景 / 启发**：
  - 个人开发者或小商户想给自己的系统做"到账自动确认"（比如虚拟商品自动发货），又拿不到官方商户资质时的现实解法。
  - 对做支付对接的人，它是一个"通知驱动的状态机"样本：订单有效期、金额匹配、幂等回调、设备健康度，四件事缺一不可。
  - **风险必须看清三条**：其一，可靠性依赖手机——设备停机或通知没进通知栏就确认不了，可能漏报或错配，作者自己也要求"以实际到账记录为准"；其二，仓库仅 14 Star、刚创建不久，用于正式收款前必须自测；其三，与支付宝、微信无隶属关系，合规责任在部署者，密钥、设备令牌与交易数据都要自己保护好。

**它是什么**

> ANE （Automated Notification-Driven Epay） 是一个自托管的收款订单匹配服务。Android 设备监听支付宝和微信的收款通知，服务端按渠道、实付金额和订单有效期匹配订单，再向业务系统发送易支付回调。

**资金与接口边界**

> ANE 使用你自己的固定收款码，不代收资金，也不调用官方支付 API。

**可靠性的前提**

> Android 后台监听依赖手机供电、网络和系统权限。设备停机，或通知未进入系统通知栏时，ANE 无法确认该笔收款。

**回调的规矩**

> 回调通过 GET 发送。业务系统应验签、检查订单及金额、幂等处理，再回复 HTTP 2xx 和正文 `success`。浏览器返回页不能代替服务端回调。

**签名规则**

> 签名时排除 `sign`、`sign_type` 和空字段；将解码后的参数按名称 ASCII 升序以 `key=value&key=value` 拼接，直接附加应用密钥，计算 UTF-8 MD5 的小写十六进制。

**免责声明**

> ANE 是独立项目，与支付宝、微信支付及其运营方无隶属或合作关系。ANE 不经手资金，也不能代替支付平台账单或官方支付接口。订单匹配依赖设备收到的系统通知；通知缺失、延迟或设备离线时，可能漏报或错配。请以实际到账记录为准，并在用于正式收款前验证流程。
